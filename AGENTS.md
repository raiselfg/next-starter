## Структура страниц и компонентов

Размещай код рядом с местом его использования. Для кода, относящегося только к конкретной странице или маршруту, используй приватные папки рядом с `page.tsx`: `_components` для компонентов, `_lib` для вспомогательной логики и аналогичные папки по назначению. Внутри папки компонента размещай его файл, вложенные компоненты, константы и другие относящиеся к нему файлы рядом друг с другом. Создавай такие папки по необходимости.

Например:

```text
app/orders/
├── page.tsx
├── _lib/
└── _components/
    └── footer/
        ├── footer.tsx
        ├── components/
        │   └── footer-modal.tsx
        └── constants/
            └── links.ts
```

Общие для нескольких страниц компоненты и утилиты размещай в существующих общих каталогах проекта, например `components/` и `lib/`. Не переноси существующий код без необходимости для задачи.

## Стек проекта

- Основа: Next.js с App Router, React, TypeScript и pnpm.
- Интерфейс: Tailwind CSS, shadcn с Base UI и иконки Lucide. Многоязычность и дополнительные требования к доступности определяются по потребности проекта.
- Качество кода: ESLint и Prettier. Тестовый стек пока не используется.
- Данные: отдельный внешний API и HTTP-клиент ofetch. По умолчанию выполняй запросы на сервере Next.js; запросы из браузера используй, когда этого требует интерфейс или контракт API.
- Изменение данных: предпочитай Server Actions, если это подходит сценарию и контракту API.
- Кеширование: используй возможности Next.js; необходимость кеширования и его срок определяй для каждого запроса в зависимости от требований к свежести данных.
- Формы и валидация: React Hook Form и Zod. Проверяй внешние данные на границах приложения, включая ответы API, данные форм, параметры URL и переменные окружения. Некорректный ответ API считай ошибкой и не передавай дальше в интерфейс; уже проверенные внутренние данные не нужно повторно проверять на каждом шаге.
- API-клиент: общие настройки и обработку ошибок размещай в `lib/`, запросы конкретной страницы — рядом с ней в `_lib`. Авторизация и формат ошибок определяются контрактом API.
- Библиотеку общего состояния и платформу развёртывания заранее не выбираем.

## Дизайн и анимации

- Создавай выразительный, современный дизайн, соответствующий задаче и продукту. Используй компоненты shadcn и существующие CSS-переменные как основу, адаптируя их внешний вид под проект.
- Поддерживай понятную визуальную иерархию, читаемый контраст, согласованные отступы и типографику, заметные состояния интерактивных элементов и единый характер эффектов.
- Обеспечивай адаптивность на всём диапазоне ширин: смартфоны, планшеты, ноутбуки и большие экраны. Учитывай переполнение, читаемость и удобство нажатия на сенсорных устройствах.
- Используй преимущественно умеренные анимации для обратной связи, переходов и направления внимания; более выразительные эффекты добавляй там, где они уместны. Избегай ненужных бесконечных анимаций и задержек в работе интерфейса.
- Для простых переходов используй CSS и Tailwind, для сложных анимаций — Motion. Где возможно, предпочитай анимацию `transform` и `opacity` и не запускай невидимые декоративные эффекты без необходимости.
- Для подходящих визуальных задач используй [Shaders для React](https://shaders.com/react). Размещай шейдер в клиентском компоненте и подключай тяжёлые эффекты только там, где они нужны. Предусматривай статичную замену при недоступности WebGPU, уменьшении движения или проблемах производительности.
- Учитывай `prefers-reduced-motion`: заменяй выразительные анимации спокойными переходами или статичными состояниями. Интерфейс должен оставаться работоспособным без декоративных эффектов.
- При изменении интерфейса проверяй его в браузере на нескольких ширинах, включая смартфон, планшет и десктоп. Проверяй уменьшение движения и, при использовании шейдера, состояние без WebGPU. Если браузерная проверка недоступна, укажи это в отчёте.

## Объём изменений

Вноси только минимальные изменения, необходимые для полного и корректного выполнения задачи. Не добавляй несвязанную функциональность, зависимости, абстракции или попутный рефакторинг. Сохраняй существующее поведение, оформление незатронутого кода и изменения пользователя; необходимые изменения соседнего кода ограничивай решением задачи. Перед завершением проверь дифф и убедись, что каждое изменение обосновано задачей.

## Компоненты интерфейса

Для стандартных элементов интерфейса, таких как поля ввода, кнопки, диалоги и выпадающие списки, сначала используй уже добавленные компоненты shadcn из `components/ui/`. Если нужного компонента в проекте нет, добавь его из shadcn с учётом существующей конфигурации проекта и доработай под задачу. Не создавай самодельную замену, когда подходящий компонент shadcn доступен. Если подходящего компонента нет, согласуй решение с пользователем.

## Качество кода

- Перед реализацией изучай относящийся к задаче код и похожие решения в проекте. Переиспользуй существующие компоненты и логику, следуй принятым подходам и не дублируй их без необходимости.
- Для страниц предусматривай состояния загрузки и непредвиденной ошибки с помощью файлов `loading.tsx` и `error.tsx` App Router. Размещай их на подходящем уровне маршрута, учитывая область действия существующих границ. Состояние загрузки должно соответствовать странице, а состояние ошибки — быть понятным пользователю и предоставлять повторную попытку, когда она уместна. Следуй документации установленной версии Next.js.
- По умолчанию используй Server Components; добавляй `'use client'` там, где необходимы интерактивность или браузерные API. Не передавай на клиент секреты и серверные данные, которые ему не нужны.
- Используй семантические HTML-элементы, подписи полей, видимый фокус и управление с клавиатуры.
- Давай понятные имена, выделяй повторяющуюся логику при реальной необходимости и в комментариях объясняй причины неочевидных решений, а не пересказывай код.
